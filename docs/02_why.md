
## Обоснование связей диаграммы классов TaskFlow ##

TaskList — Task — композиция (*--): задачи живут внутри списка — в коде это vector<unique_ptr<Task>> tasks_; список создаёт, хранит и удаляет задачи, без списка они не существуют. Ромб стоит у целого (TaskList).

Menu — TaskList — ассоциация (-->), кратности 1 — 1: в программе один список задач, и меню ссылается на него по указателю taskList_: он не создаёт список и не управляет его временем жизни — поэтому ассоциация, а не композиция.

TaskList → TaskFilter — зависимость (..>): фильтр нужен списку только внутри метода findBy(filter) как параметр; TaskList не хранит TaskFilter в полях.

TaskFilter → Task — зависимость (..>): фильтр получает задачу только в параметре метода matches(task) и обращается к её методам matchesTag, matchesDate, matchesPriority; самих задач он не хранит.

ITaskStorage → Task — зависимость (..>): интерфейс получает задачи в параметрах save(list, path) и load(list, path); где задачи лежат на самом деле, решают реализации.

TxtTaskStorage ..|> ITaskStorage и CsvTaskStorage ..|> ITaskStorage — реализация интерфейса: интерфейс содержит только чисто виртуальные методы save/load, каждое хранилище выполняет этот контракт под свой формат — TXT или CSV; треугольник направлен к интерфейсу. Базовый класс FileStorage между ними не введён намеренно: семейства TXT и CSV создаются фабрикой по отдельности и не зависят друг от друга.

Task → Priority — зависимость (..>): атрибут priority имеет тип перечисления Priority (High / Medium / Low) — фиксированный набор значений, чем меньше номер, тем важнее.

Task → Status — зависимость (..>): атрибут status имеет тип перечисления Status (New / InProgress / Done) — статусы жизненного цикла задачи с диаграммы состояний из ДЗ-3.

TaskFilter → Priority — зависимость (..>): критерий поиска по приоритету — поле priority_ типа Priority.
