
# Обоснование связей диаграммы классов TaskFlow

**TaskList — Task — композиция (`*--`)**: задачи живут внутри списка — в коде это `vector<Task> tasks_`; список создаёт, хранит и удаляет задачи, без списка они не существуют. Ромб стоит у целого (TaskList).

**User — TaskList — ассоциация (`-->`), кратности 1 — 1**: у каждого пользователя ровно один список задач. В коде это указатель `TaskList* taskList_`: пользователь ссылается на чужой объект и не управляет его временем жизни — поэтому ассоциация, а не композиция.

**TaskList → TaskFilter — зависимость (`..>`)**: фильтр нужен списку только внутри метода `findBy(filter)` как параметр; TaskList не хранит TaskFilter в полях.

**TaskFilter → Task — зависимость (`..>`)**: фильтр получает задачу только в параметре метода `matches(task)` и обращается к её методам `matchesTag`, `matchesDate`, `matchesPriority`; самих задач он не хранит.

**Reminder → Task — зависимость (`..>`)**: напоминание получает список задач в параметре `check(tasks, today)`, отбирает те, чей срок наступил, и возвращает; ничего не хранит.

**ITaskStorage → Task — зависимость (`..>`)**: интерфейс получает задачи в параметрах `save(tasks)` и `load()`; где они лежат на самом деле, решают реализации.

**FileStorage ..|> ITaskStorage — реализация интерфейса**: интерфейс содержит только чисто виртуальные методы `save`/`load`, FileStorage выполняет этот контракт; треугольник направлен к интерфейсу.

**CsvTaskStorage --|> FileStorage — наследование**: CSV-хранилище — разновидность файлового: наследует защищённое поле `filename_` и переопределяет `save`/`load` под формат CSV; треугольник у родителя.

**Task → Priority — зависимость (`..>`)**: атрибут `priority` имеет тип перечисления Priority (LOW / NORMAL / HIGH) — фиксированный набор значений.

**Task → TaskStatus — зависимость (`..>`)**: атрибут `status` типа TaskStatus — статусы жизненного цикла задачи с диаграммы состояний из ДЗ-3.

**TaskFilter → Priority — зависимость (`..>`)**: критерий поиска по приоритету — поле `priority_` типа Priority.
